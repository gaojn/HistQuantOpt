1. 结论先行

「cvxpy 太慢」这个判断只对了一半。cvxpy 的建模 + 编译（canonicalization）每期只花 约 0.13s（占 6%），真正的瓶颈是 CLARABEL 内点法求解器本身：在全市场 N≈5,366 只股票、51 因子的 QP 上每期跑 1.4~2.1s，占逐期循环的 84%。 所以「绕开 cvxpy / 手写求解器接口」收益上限只有 ~6%，方向错了； 正确的杠杆是「换更快的 QP 求解器」＋「缩小问题规模」，两者相乘。

在真实调仓期问题上实测（非合成数据），推荐组合方案：

  • 方案一：求解器换 PIQP（CLARABEL 降级兜底）——单独 3.5~4.2x，改动只有一个函数，半天可上线；
  • 方案二：候选池瘦身（alpha top-1000 ∪ 持仓 ∪ 基准股 ∪ 成分股容量）——单独 3~5x， 实测解逐票一致（持仓重叠 100%，权重 L1 差 0.0000）；
  • 两者叠加：求解环节 10~12x，全部 12 个测试期 status=optimal，目标值差 < 1e-7（求解器噪声量级）。

4. 落地建议（按优先级）

1求解降级链改为 PIQP → CLARABEL → SCS 3.5–4.2x 改动 ≈ 1 个函数

只改 hqopt/optimizer/_common.py 的 solve_with_fallback，两个优化器共用，一处生效：

# hqopt/optimizer/_common.py
_PIQP_KW = dict(eps_abs=1e-7, eps_rel=1e-7)   # 求解后门禁 1e-5，留两个量级余量

def solve_with_fallback(problem: cp.Problem) -> str | None:
    """PIQP → CLARABEL → SCS 三级降级。

    PIQP 是纯 QP 求解器：te_upper / vol_upper 的二次硬约束会抛
    SolverError（实测验证），自动落到 CLARABEL——语义不变，只是变慢。
    """
    try:
        problem.solve(solver="PIQP", **_PIQP_KW, verbose=False)
        if problem.status in _OPTIMAL_STATUSES:
            return None
    except Exception:
        pass          # 二次约束模式 / PIQP 未安装 → 降级

    try:
        problem.solve(solver=cp.CLARABEL, max_iter=_CLARABEL_MAX_ITER, verbose=False)
        if problem.status in _OPTIMAL_STATUSES:
            return None
    except Exception:
        pass

    try:
        problem.solve(solver=cp.SCS, max_iters=_SCS_MAX_ITERS, verbose=False)
    except Exception as exc:
        return f"all solvers failed: {exc}"
    return None
  • pyproject.toml 增加依赖 piqp>=0.6（纯 pip wheel，无系统依赖）。
  • 同步更新 tests/test_solver_fallback.py（当前只覆盖 CLARABEL→SCS 两级）。
  • 已验证的边界：te_upper/vol_upper 模式（二次硬约束）PIQP 会抛 SolverError，链条自动回落 CLARABEL；现有 1e-5 求解后硬约束门禁继续对所有求解器兜底。

2候选池瘦身：alpha top-M 预筛 再乘 3x，合计 10–12x 需全区间影子验证

在 _solve_period 进优化器之前（或 filter_universe 增加一档），把优化域缩到：

def candidate_pool_mask(alpha, snapshot, prev_weight, bm_weight=None, top_m=1000):
    """alpha top-M ∪ 当前持仓 ∪ 基准股 ∪ 成分股容量兜底。"""
    rank = pd.Series(alpha).rank(ascending=False).values
    keep = rank <= top_m
    if prev_weight is not None:
        keep |= prev_weight > 1e-12     # 持仓必须在池内：卖出/冻结/只卖约束都挂在它身上
    if bm_weight is not None:
        keep |= bm_weight > 1e-10       # 指增：基准股保留，主动偏离/行业约束才有意义
    cmask = snapshot.constituent_mask
    crank = pd.Series(np.where(cmask, alpha, -np.inf)).rank(ascending=False).values
    keep |= (crank <= int(top_m * 0.6)) & cmask   # 成分下限容量：0.6M×1% ≫ 40%/80%
    return keep
  • 为什么无损：纯多头 + 线性 alpha + 凸惩罚下，深度负 alpha 股票不会进最优解的支撑集； 约束相关股票（持仓/基准/成分）已显式保留。实测 4 个稳态期解逐票一致。
  • 上线前必须做：用 2020–2026 全区间跑一次影子对比（全池 vs 瘦身池），核对每期权重 L1 差 与 NAV 曲线；本报告附带的 bench/bench_reduce*.py 即为对比工具原型。
  • 建议做成配置项（如 universe.alpha_top_m: 1000，null=关闭），风险模型 risk_model.at() 按瘦身后 tickers 取切片即可（已验证该用法）。
  • M 的安全边际：组合仅持 ~110 只，M=1000 已有 9 倍余量；保守可先上 M=1500（2.5–3x）。

4.5 落地补记（分支 perf/piqp-candidate-pool 实现时的两个修正）

实现阶段的全流程回放（含成交账本串行推进）暴露了本报告 §3.2 瘦身规则的两个盲区， 已在代码中修复，最终两个策略在 6 个月窗口的新旧 weights.parquet 每期 L1 差 ≤ 1.3e-4（求解器噪声级）：

  • 风格对冲票：alpha_max 的绝对风格约束（Size/Beta 等 ≤ ±0.2σ）binding 时， 全池最优解持有 ~4%权重、alpha 排名 1800~2400 的「对冲票」（全部为大市值成分股）， 纯 alpha top-M 池会漏掉它们，首期即漂移 0.16 L1。 修复：池规则增补「每个风格因子载荷两端各 60 只」，实测恢复逐票一致。 安全池由 ~1300 增至 ~2450（alpha_max）/ ~2830（index_enhance）， 瘦身提速由 3~5x 回落至 2~5x（叠加 PIQP 后组合提速约 4~8x， 而非 §3.3 用非安全池测得的 10~12x）。
  • 成本向量口径：build_cost_vector 按池内中位数归一化， 瘦身后重算会改变同一只股票的换手成本定价（index_enhance 曾漂移 9e-3 L1）。 修复：成本向量在瘦身前于全池计算、随池切片，绝不重算。

教训与报告结论一致：瘦身的安全边界在「约束相关股票」， 而约束相关性不止持仓与基准——任何 binding 约束的松弛贡献者都必须留在池内。 等价性已固化为单元测试（tests/test_candidate_pool.py，含紧风格约束场景）。
